# GreekGod 4.0 Windows signing readiness

Audit date: 2026-09-27. Windows Authenticode signing blocker: **OPEN**. No
artifact was signed and no certificate, key or provider credential was created,
requested, imported or stored during this phase.

## Third-party boundary

The 24 qualified llama.cpp b10760 runtime PE files, including
`llama-server.exe`, its DLLs and `libomp.dll`, are unsigned upstream. They are
third-party, contract-bound AI Pack inputs and are **excluded** from GreekGod
signing. Signing any of them would change bytes and SHA-256 and would require a
new AI Pack contract, new hashes and full requalification. The preferred policy
is to preserve the approved pack byte-for-byte.

The three pinned VC runtime files (`msvcp140.dll`, `vcruntime140.dll`,
`vcruntime140_1.dll`) have valid Microsoft Authenticode signatures, Microsoft
certificate chains, SHA-256 file digests and Microsoft RFC3161/SHA-256
timestamps. Their leaf signer is `Microsoft Windows Software Compatibility
Publisher`; SignTool `/pa` passes. They are excluded from GreekGod signing.
WebView2 is Microsoft-owned and is not re-signed; the current NSIS policy uses
the Tauri download bootstrapper rather than shipping GreekGod-owned WebView2
binaries. Other NSIS/Tauri/Windows third-party components are likewise not
automatically re-signed merely because they are packaged.

## Required signing order and Tauri integration

The production order is immutable:

1. build `greekgod.exe` and `greekgod-sync-service.exe`;
2. sign and verify both GreekGod-owned inner executables;
3. stage the signed Sync Service as the Tauri `externalBin` input;
4. run Tauri/NSIS bundling with signing enabled so NSIS signs its generated
   uninstaller during generation;
5. sign the final setup executable;
6. install that exact setup in an isolated target and verify Desktop, Sync
   Service, uninstaller and setup;
7. compute and publish final release SHA-256 values only after signing and
   timestamping.

GreekGod uses `@tauri-apps/cli` 2.11.4, Rust `tauri` 2.11.5 and the checked-in
CLI schema. The schema supports `bundle.windows.certificateThumbprint`,
`digestAlgorithm`, `timestampUrl`, `tsp` and `signCommand`. The installed schema
defines `tsp: true` as RFC3161. The installed Tauri-generated NSIS source proves
support for signing the generated uninstaller, and the Tauri bundler signs the
finished NSIS setup. The Sync Service is built and copied by GreekGod's
`prepare-sync-service.mjs`; it must be explicitly signed and verified before it
is handed to Tauri. It is not safe to assume an arbitrary external sidecar is
covered by signing the outer installer.

| Tauri/NSIS output | Installed-version behavior | GreekGod requirement |
| --- | --- | --- |
| main Desktop executable | Tauri signs it when Windows signing is configured | verify it before bundling and again after isolated install |
| `externalBin` Sync Service | no verified automatic-signing guarantee in this pipeline | explicit pre-bundle signing step is required |
| final NSIS setup | Tauri bundler signs it when signing is configured | verify after bundling |
| generated NSIS uninstaller | Tauri injects the configured command through `!uninstfinalize` | verify actual `uninstall.exe` after isolated install |

`tools/windows-signing/tauri-windows-signing.template.json` is inert,
provider-neutral scaffolding. It pins SHA-256 and RFC3161 but deliberately leaves
thumbprint, timestamp URL and custom command unresolved. It is not used by the
current build.

## Cryptographic and key policy

- Authenticode file digest: SHA-256 only; never SHA-1.
- Timestamp: RFC3161 only, with SHA-256 timestamp digest.
- Verification: Windows application policy (`signtool verify /pa /all /v`),
  exact selected publisher subject, embedded RFC3161 OID/timestamp and SHA-256.
- The production key never enters source control, logs, release files, the
  installer, AI Pack or normal GreekGod runtime access.
- A PFX, if a chosen service legitimately provides one, remains outside the
  repository; its password comes only from protected secret storage and all
  temporary material is securely removed. Modern publicly trusted code-signing
  issuance normally requires HSM/token protection rather than an exportable PFX.
- Hardware, cloud and HSM identities/credentials stay outside source control;
  CI uses least privilege and short-lived/federated identity where supported.

No timestamp URL is selected until the provider is selected and its RFC3161
endpoint is verified.

## Provider integration profiles

### Traditional publicly trusted OV/EV identity

This works with Tauri's Windows certificate-store path through
`certificateThumbprint`, `digestAlgorithm`, `timestampUrl` and `tsp`, or through
a provider CLI wrapped by `signCommand`. Since June 2023, CA/Browser Forum rules
require publicly trusted code-signing private keys to be protected in a suitable
hardware crypto module/token. Local signing is feasible when the token/provider
CSP is available; unattended CI depends on the vendor's remote-HSM service and
automation support. Timestamping and renewal remain recurring operations.
Microsoft's current public comparison estimates OV at USD 150–300/year and EV at
USD 400+/year, but an actual quote and individual eligibility must be obtained
from the selected CA. EV no longer receives automatic SmartScreen reputation.

### Provider-neutral remote/cloud/HSM command

Tauri `signCommand` replaces `%1` with each file path, so a remote signer CLI
can sign the app/setup and be injected into NSIS's uninstaller finalize step.
This supports local developer or CI signing only when the selected provider's
client and authenticated identity are present. The integration must preserve
noninteractive error codes, SHA-256/RFC3161 policy, exact-publisher verification,
audit logs without secrets, service quotas, credential rotation and provider
availability. Cost and geographic eligibility are provider-specific; none is
claimed without a selected service.

### Azure Artifact Signing

Current Tauri documentation supports Azure Artifact Signing through
`artifact-signing-cli` in `signCommand`; Azure client/tenant credentials or an
approved workload identity remain external. It supports local and CI use, needs
no USB token, and supplies managed short-lived certificates/timestamping. Current
Microsoft public pricing is USD 9.99/month for Basic (5,000 signatures) and USD
99.99/month for Premium (100,000), then USD 0.005/signature above quota. A paid
Azure subscription is required. Public Trust organization validation is
available in the USA, Canada, EU and UK; individual validation is currently USA
and Canada only. Therefore an individual account in Poland is not currently
eligible, while a qualifying EU organization may be. Account, region, identity
validation, role assignment and recurring Azure operations must be confirmed.

No option is selected or ranked by this audit. Sources:
[Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/),
[Tauri configuration](https://v2.tauri.app/reference/config/),
[Microsoft signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options),
[Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart),
[Artifact Signing pricing tiers](https://learn.microsoft.com/en-us/azure/artifact-signing/how-to-change-sku),
[CA/Browser Forum requirements](https://cabforum.org/working-groups/code-signing/requirements/).

## Verification and unsigned-final guard

`tools/windows-signing/Verify-WindowsReleaseSigning.ps1` is credential-free and
Windows PowerShell 5.1 compatible. It checks artifact cardinality, Windows
application-policy validation, exact configured publisher, SHA-256 Authenticode,
timestamp presence, the embedded RFC3161 timestamp OID and SHA-256 timestamp
digest. It requires an isolated installed uninstaller and validates every byte of
the Offline AI Pack against the approved contracts. It also rejects unexpected
GreekGod-named PEs in the final artifact root.

`Final` mode fails closed when the publisher is unresolved, any required file or
uninstaller evidence is absent, any GreekGod-owned PE is unsigned/invalid,
timestamp policy fails, or the AI Pack differs. `RC` and `Development` modes
explicitly permit absent signatures but still reject a present invalid signature
and can validate a supplied AI Pack. These modes cannot silently authorize a
FINAL release. The checked-in artifact name is deliberately pinned to RC1; the
separately approved final-version change must update it to the exact final setup
name, preventing a wildcard from selecting a stale historical installer.

The current unsigned output passes explicit RC inspection and fails FINAL with
`SIGNATURE_REQUIRED`. Tests also exercise a valid signed/timestamped fixture and
detect a byte-tampered signed fixture. No private signing dependency and no
application network call were introduced.

## Installer, upgrade and artifact identity

Signing does not change current-user install mode, hooks or Sync Service
lifecycle choreography. It does change bytes/hashes of the two inner executables,
the generated uninstaller and final setup. The known blank-page/uninstaller UX
issue remains separate; its future fix must happen before final signing, followed
by a rebuild, re-sign and upgrade retest. Physical 3.0.3 -> 4.0 testing must use
the exact signed setup because signed inner bytes differ from RC1.

Artifact identity has three explicit stages: unsigned build output,
signed/timestamped output, and the final release SHA-256 over the signed bytes.
Unsigned hashes are build evidence only and must never be published as final
release hashes. Historical RC1 hashes remain unchanged historical evidence.

## SmartScreen boundary and open decision

Authenticode proves publisher identity and detects post-signing modification. A
trusted RFC3161 timestamp preserves validation based on the certificate being
valid at signing time after ordinary certificate expiry; it does not preserve
trust after revocation or prove application safety. SmartScreen separately uses
publisher and file reputation. A newly issued OV, EV or Artifact Signing identity
may still show an unrecognized-app warning; signing does not guarantee immediate
reputation. See [Microsoft SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

The product owner must still decide the legal publisher identity and exact
subject, distribution channel, provider model, local versus CI signing authority,
credential custody/recovery, timestamp service, budget and renewal/continuity
owner. Only then can provider-specific configuration be approved.

The blocker remains **OPEN** until a real identity/provider is provisioned, exact
final artifacts are signed and RFC3161 timestamped, the final verifier passes,
the signed upgrade path is physically accepted, and post-signing hashes are
recorded.
