# GreekGod 4.0 Windows installer upgrade UX

Audit and implementation date: 2026-09-27. Physical validation date: 2026-09-28.
Implementation status: **COMPLETE; PHYSICALLY VALIDATED**. Windows installer
upgrade/uninstaller UX blocker: **CLOSED**. No production installation or
production AppData was used during implementation or kit preparation.

## Observed behavior and exact cause

The accepted RC1 rehearsal physically observed the sequence: license page,
effectively blank/hidden incoming installer, visible old-version uninstaller,
then a successful upgrade with intact data and deterministic schema migration.
The original machine evidence was not retained; that result remains an
operator-attested observation.

The generated Tauri CLI 2.11.4 NSIS source explains the sequence exactly:

1. `PageReinstall` detects the current-user installation through
   `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\GreekGod` and
   `HKCU\Software\Igor Pich\GreekGod`.
2. A normal graphical launch has neither `/UPDATE` nor `/P`, so the first
   upgrade choice enters `reinst_uninstall`.
3. `HideWindow` hides the incoming installer and `ExecWait` invokes the
   registered old `uninstall.exe` without `/UPDATE` or `/P`.
4. The old uninstaller is therefore interactive and owns the visible foreground
   while the incoming installer waits. The hidden/page-transition state accounts
   for the unexplained blank-looking interval.
5. Only after the old uninstaller exits does the incoming installer return,
   choose the install directory, execute the existing preinstall Sync Service
   hook, replace files, write the new uninstaller/registration, and execute the
   postinstall Sync Service hook.

The GreekGod hooks did not create the blank page. They ran later inside the
stock uninstall/install sections. Under the previous choreography the old
uninstaller could remove the installed executables, resources and registration
before the incoming installer had copied its replacement. AppData deletion was
still suppressed unless explicitly selected and never occurs in update mode.

## Implemented behavior

GreekGod now checks in the exact upstream Tauri CLI 2.11.4 NSIS template and
selects it through Tauri's supported `bundle.windows.nsis.template` setting.
The maintained delta is limited to an older NSIS installation:

- show a concise Polish/English update page stating that the existing version
  will be replaced in place, user data is preserved, and manual uninstall is
  unnecessary;
- set Tauri's existing internal `UpdateMode` and continue directly to the
  install section;
- do not hide the incoming installer, start the previous uninstaller, or wait
  for a second foreground installer UI.

Same-version maintenance, deterministic downgrade choices, WiX migration,
current-user installation, install-directory restoration, Tauri's generated
uninstaller, and all GreekGod lifecycle hooks retain their prior behavior. The
package identifier remains `com.igorpich.formlog` and the default install path
remains `%LOCALAPPDATA%\GreekGod`.

In the new path the incoming preinstall hook stops the exact installed Sync
Service before replacement. It uses the installed lifecycle script where
available and retains the existing scheduled-task fallback. Files are then
replaced in place. The postinstall hook installs the new task/rules and starts
the new service. Its existing failure path restores the backed-up previous Sync
Service executable, attempts to recover service state, aborts visibly, and
never deletes the database.

Cancelling on the detected-upgrade page is a controlled pre-install failure:
the page precedes `Section Install`, so no lifecycle hook, file replacement or
AppData operation has executed. The physical cancellation rehearsal passed:
3.0.3 remained installed and launchable, its schema-7 data remained unchanged,
and its Sync Service integration remained coherent.
