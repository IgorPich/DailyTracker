## Accepted 4.0 product contract

The current user's persisted A/B/C/D program is unchanged by upgrade. No automatic
template creation, removal, rename, reordering, new IDs or exercise replacement.
Historical workouts remain snapshots. A/B/C/D may remain fresh-install defaults, but
seed content is not a runtime count limit, identity scheme or strategic rule.
Template count is dynamic (1, 4, 5, 8 or another reasonable count), names are user data,
and order is persisted user configuration. No program letter implies training semantics.

The current user's journal configuration remains unchanged by upgrade. Eventually users
choose metrics; disabling one never deletes historical measurements. Analytics must
eventually distinguish MISSING_DATA from NOT_TRACKED. Waist, chest, biceps, steps and
nutrition are examples, not universal tracking priorities. Configurable Journal is a
separate reviewed slice: no measurement fields, schema, config or Analytics changes here.

## STOP: safe multi-template application integration is missing

Evidence:

- `AppContext.tsx`: updateTemplate and replaceData return void; replaceData delegates to
  the ordinary setData/coordinator update path.
- `desktopDataCoordinator.ts`: ordinary update publishes React immediately and invokes
  store.save without awaiting it at the UI boundary. It cannot provide Save Program
  acknowledgement, bind the original sandbox program or reconcile uncertain outcomes.
- `confirmedTrackingMutation.ts`: the safe capability exposes only changeTemplateRepRange.
- `nativeAuthorityBridge.ts`: that narrow operation performs fresh read/validation/CAS
  inside the shared queue; ordinary save accepts a complete AppData snapshot and uses
  the adapter's revision when it executes.
- `authoritative_repository.rs::replace_authoritative_snapshot`: SQLite already supports
  an atomic multi-entity transaction, global expected-revision check, one change-set,
  per-entity revisions/outbox, materialization and commit. The database is NOT the blocker.

Passing an old sandbox AppData to replaceData/save risks replacing unrelated newer data.
Separate caller-side load/check/save calls do not bind verification and persistence in
one queue operation. Repeated updateTemplate calls are not one coherent user transaction.
None of these shortcuts is used or implemented.

### Proposed narrow extension, pending approval

A Desktop-only `saveProgram` operation (not a Companion command/action):

1. Accept the original program state fingerprint and a validated draft template array.
2. Join the existing authoritative queue and load current authority inside it.
3. Compare current templates/order with the original snapshot; mismatch returns STALE.
4. Validate unique template/slot identities and references against current definitions.
5. Replace only templates on the fresh aggregate; preserve workouts, definitions, journal,
   settings and all unrelated fields exactly.
6. Reuse existing single authoritative replacement/CAS transaction and await its result.
7. Reconcile React without duplicate save; coordinate ordinary writes as existing confirmed
   mutations do. Distinguish acknowledged success, STALE, FAILED and INDETERMINATE.
8. Keep unsafe legacy/browser execution blocked, while allowing a non-persisting sandbox.

No new SQL, schema, sync protocol, generic patch API or Companion mutation is needed.
The extension and builder have not been implemented pending the requested STOP review.

## Current DailyEntry / next Configurable Journal audit

`packages/core/src/types.ts` defines id/date and optional weight, calories, protein, fat,
carbs, steps, waist, sleep, recovery, note. There is no metric-definition registry,
tracking-enabled configuration or NOT_TRACKED state.

Hardcoded consumers inspected:

- Desktop Journal NumericKey, input metadata, priorities and table cells enumerate weight,
  waist, calories, protein, fat, carbs, steps; current priorities are presentation constants.
- Mobile JournalPage and mobileModel enumerate numeric fields/units/integer handling.
- Desktop calculations has weight/waist-specific selectors; CoachReport uses waist charts
  and summary fields directly. Dashboard/Progress and exports also need the next audit.
- Desktop CSV export fixes its columns to date, weight, nutrition, steps, waist and note;
  sleep/recovery exist in the shared model but are not in that current export list.

Native sync uses a `daily_entry` entity identified by date, with the full JSON payload,
entity revision and order metadata. It does not have one SQLite column per metric.
Training templates similarly use `training_template` entities identified by ID.
JSON payload extensibility does NOT by itself establish old-client compatibility.

Safest next direction: retain existing DailyEntry fields/history unchanged; introduce an
explicit versioned metric/visibility contract with existing configuration as defaults,
and define how effective tracking periods distinguish missing observations from untracked
metrics. Disabling affects future collection/presentation, not historical deletion or
retroactive erasure. Generic measurements need a separately reviewed AppData contract,
validation, adapters, UI, exports and old-client round-trip tests. A new entity type would
also require updating closed sync entity discriminators; extending daily_entry payload
may avoid that, but must not be assumed safe without compatibility tests. No schema or
protocol migration is implemented or approved by this preflight document.
