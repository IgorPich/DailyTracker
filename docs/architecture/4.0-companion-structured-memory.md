# Companion structured memory v1

Foundation: `8fd6f062954365142f90c982a98a3b67d4bfee38`. Existing checkpoints remain
unchanged. Memory is PC-local and outside Tracking, HumanCoach persistence and sync.

## Deliberately small contracts

`MemoryItem`: id, typed content, scope, nullable expiresAt, source, createdAt,
provenance `{ acceptedBy: 'USER', sourceId }`, status ACTIVE or ARCHIVED.
All fields are closed/validated. IDs are opaque exact references, timestamps canonical
UTC. Unknown fields/kinds, duplicate IDs, invalid dates and invalid provenance fail closed.

Content has just two alternatives:

- SUMMARY_STYLE with SHORT or DETAILED: a communication preference, never a training rule.
- HUMAN_COACH_REFERENCE with an exact CoachNote/Task/Target/Decision ID: a pointer, not
  copied trainer strategy. It does not promote a draft to an authoritative decision.

Sources: USER_EXPLICIT for manually entered preferences; HUMAN_COACH for explicitly
accepted source references; COMPANION_SUGGESTED for explicitly accepted fake candidates.
HumanCoach provenance points to the exact original item; suggested provenance retains
the candidate ID. Accepted contents/provenance are immutable; archive and add a new
item to change a preference. No confidence score is invented for this deterministic v1.

Scopes: GLOBAL, EXERCISE with exact current ExerciseDefinitionId, HUMAN_COACH_CONTEXT
with exact current Coach item ID. TEMPLATE is deferred because no v1 content needs it.
Creation and active reading require an unambiguous current reference. Deleting an entity
excludes its memory from context without deleting the inspectable memory record.

## Candidates and lifecycle

FakeCompanionModel receives a MEMORY_SUGGESTION request with the closed style choices,
not repository/review/executor capabilities. Its unknown response must validate as a
MemoryDraft; v1 suggestions support global summary preferences only. No parsing or
automatic extraction. Candidate generation and rejection write nothing.

Frozen MemoryCandidate objects are registered in a private review WeakMap. Explicit
acceptance consumes that exact candidate before persistence. A copied, forged, rejected
or already consumed candidate cannot be accepted. Candidates are session-local, not
persisted memory. The management UI exposes separate prepare, accept and reject actions.

Successful acceptance creates ACTIVE memory. ARCHIVED is explicit. EXPIRED is a derived
inspection status when `expiresAt <= asOf`; no automatic rewrite, normalization or
deletion. Failed/uncertain persistence never causes an automatic retry; the UI requires
refresh before another write and discards the consumed candidate. Inspect saved state
before preparing a replacement candidate. Exact active content/scope duplicates are
rejected to avoid duplicate acceptance.

## Bounded read-only context

At most 100 persisted records, including archived/expired records. Reaching capacity
fails explicitly; no hidden eviction. A future reviewed deletion/retention workflow is
needed beyond this v1 quota.

CompanionMemoryReader exposes only `readActiveMemory(scope, asOf)`. Selection includes
accepted ACTIVE records created by asOf, not expired, with valid current references,
whose scope is GLOBAL or exactly matches the request scope. Stable createdAt/ID ordering
and a maximum of 10 records bound the context. No fuzzy matching, names, embeddings,
priority inference or automatic precedence between conflicting preferences.

`withCompanionMemory` decorates the existing CompanionContextReader using only that
reader capability. It captures explicit request scope/time and supplies selected
read-only evidence DTOs including content and provenance. The model sees no memory
writer. Tests exercise the adapter through all three existing read-only handlers;
there is still no automatic dialogue/event subscription or chat UI.

Memory content is inert data, never an action. The existing command module does not
import memory: exact current target allowlists, state binding and confirmation remain
unchanged. Read-only dialogue/spontaneous/application-event paths remain mutation-free.

## Local persistence and recovery

Native authority is Tauri AppData, not Tracking AppData:

- Installed identifier `com.igorpich.formlog`: `greekgod-companion-memory.v1.json`.
- Dev identifier `com.igorpich.formlog.dev`: `greekgod-companion-memory.dev.v1.json`.
- File envelope: `{ memory: { version: 1, items: [...] } }`.
- Backup: the same filename followed by `.backup.json` in the same directory.
- Browser preview: empty inspection/candidate preview only; persistence explicitly blocked.

Import/load is lazy and never creates an empty file. A singleton repository serializes
fresh-read/validate/update/save operations; it rejects rewriting accepted provenance or
removing existing records. Full domain validation happens at the repository boundary.
The native command has fixed file paths and additionally validates the envelope/basic
record structure. It does not implement a second competing domain validator.

The native save reuses HumanCoach's tested same-directory atomic replacement helper:
write temp, flush/sync, verify bytes, atomic rename. HumanCoach's format/behavior is
unchanged; only helper visibility is shared inside Desktop infrastructure.
Before replacing memory, write and verify a byte-for-byte backup of the prior file.
First creation backs up the initial snapshot. Backup failure blocks replacement.
Interruption before replacement retains the prior authoritative bytes. Corruption or
unsupported versions fail closed; there is no automatic restore. Recovery from backup
is an explicit future/manual reviewed operation, not a hidden startup behavior.

The existing Desktop single-instance guard precedes application initialization. No
new lock is added. Source audit finds the fixed native command as the only file writer:
Sync Service, Mobile and background helpers have no memory writer. Browser is blocked;
dev uses separate path/identifier. External manual editing while Desktop runs is not a
supported writer and requires closing the application first.

## Management UI and verification

`Pamięć Companion` is a small separate management page: structured manual entry,
exact entity selection, optional expiry, fake candidate preview/accept/reject,
source/provenance inspection, archive, expired inspection and explicit refresh.
No chat redesign, free-form memory text, hidden auto-memory or command execution button.

Tests cover domain/provenance/scope/expiry/candidate boundaries, read-only context,
repository restart/serialization/corruption and browser blocking. Rust tests use only
temporary directories to verify actual replacement, nonempty-record round-trip,
previous-file backup, injected interruption and backup failure. No production memory
file is created by tests; no installed Tauri application or production data is launched.
The normal frontend build is not an installer or an interactive UI smoke test.

Deferred: real provider, memory deletion/retention policy, richer content/scopes,
conflict-resolution UX, backup recovery UI, event wiring, embeddings, transcripts,
mobile sync, avatar/ReactionCoordinator and further explicit commands.
