# Companion trainer proposals v1 — fake provider only

Foundation was fast-forwarded, preserving TrainerText commits, to `506df439be50ba1ab78f19044dbc270c6f5438a1`. This feature branch is not merged into foundation.

## Ownership and dependency direction

HumanCoach still owns all CoachNote/Task/Target/Decision entities, provenance and DRAFT/AUTHORITATIVE transitions. Companion owns only transient interpretation proposals and their validation. Desktop composes the two. Companion imports public HumanCoach types only (CoachNote and TargetSpecification); it does not import HumanCoach commands, repository or platform code. Core, Analytics and HumanCoach have no Companion dependency. No new persisted entity/field/version/file/schema or sync protocol changes.

## Model port and context

`CompanionModel.propose({ text, exercises: [{ id, name }] }): Promise<unknown>` is the entire provider port. The output is structured data, not a JSON string; parsing transport responses is a future provider responsibility. FakeCompanionModel clones a constructor-configured response and returns a fresh clone on each request, ignoring note content. It has no keyword/regex extraction, network, real LLM or command capability.

`proposeCoachDraftsFromNote({ note, exercises, allowedExerciseIds }, model)` accepts an exact TrainerText CoachNote and explicit allowlist. It checks that each allowed ID identifies exactly one contextual definition. Only note text and the allowlisted ID/name pairs are sent to the provider; not provenance, workout history, targets, aliases, gyms or other notes. Desktop currently explicitly allows all uniquely identified valid persisted definitions offered by the existing picker. The private allowlist and source binding are not shared with the provider by reference.

## Closed response schema

The raw response is an array of up to 20 objects. Unknown fields, kinds, target types, scopes and units fail; no field stripping or coercion. Required text must be non-whitespace and no longer than 20,000 characters. Plain data objects/arrays only: reject getters, sparse arrays, extra array keys and unsupported prototypes.

- TASK: `kind`, `title`, optional `description`, `exerciseIds` (zero or one exact allowed ID).
- DECISION: `kind`, `text`, `exerciseIds` (zero or one exact allowed ID).
- TARGET: `kind`, `title`, `specification` with one of:
  - REP_RANGE: `type`, `scope: EXERCISE`, `exerciseId: allowed ID | null`, positive integer `min`, integer `max >= min`, `unit: reps`;
  - BODYWEIGHT: `type`, `scope: PERSON`, finite positive `value`, `unit: kg`;
  - WAIST: `type`, `scope: PERSON`, finite positive `value`, `unit: cm`.

The v1 one-exercise limit matches the existing manual form; multiple proposed links are rejected, never truncated. No model-generated identity, provenance, acceptance, command or arbitrary metadata fields exist. Model output cannot set sourceNoteId. Missing task/decision identity is represented by an empty link array. An unresolved rep target uses null and cannot become a HumanCoach draft until the user selects an exercise. Neither names nor aliases are identity. Same-name definitions remain distinct. The application does not guess identities from text.

Policy: **reject the whole response** on any structural or semantic error. No partial proposals are returned or written. Each successful result is `ProposedCoachDraft { sourceNoteId, fields }`, with sourceNoteId bound by the application to the original note after validation. There is no stored draft ID or acceptance state yet.

## Desktop review and two explicit acceptances

TrainerText notes have an explicit “Zaproponuj szkice (fake — demonstracja)” action; ingestion never invokes extraction. The Desktop fake always returns a single generic demonstrational Task without exercise links or trainer-specific instructions. Its title explicitly requires manual completion. It does not claim to extract the source and contains no exercise/gym names, canonical IDs, target values or calorie rules.

Proposals show their source link, fields and unresolved exercise state. “Przejrzyj / edytuj i przyjmij…” opens the existing manual form; all its structured fields can be corrected. The source selector is locked during review, and command construction uses the original proposal binding rather than editable form provenance. Exercise corrections use the existing picker, never typed IDs; an explicit user choice may select a different persisted definition than the model initially proposed. HumanCoach revalidates current exact IDs at draft creation and acceptance.

“Przyjmij propozycję jako szkic (DRAFT)” creates only the existing HumanCoach draft command through a Desktop adapter. A separate existing acceptance action is required for AUTHORITATIVE. Reject only removes local proposal state; leaving the screen also drops proposals. No proposal persistence, memory, deduplication or automatic execution. The unchanged repository protects source notes.

## Safety verification and deferred decisions

Companion has no storage/domain-command capability and receives no Tracking writer. Tests exercise valid/malformed/unknown/forged output, exact runtime IDs and same-name definitions, source spoofing, unresolved references, context minimization, provider input mutation, deterministic output, hostile structures and dependency direction. Desktop tests verify zero writes on extraction/rejection/invalid mixed responses, edited acceptance producing a source-linked DRAFT, separate AUTHORITATIVE acceptance, source linkage after repository reload, unresolved target blocking and existing picker/source-lock wiring. Tests use isolated memory storage, not production data.

Deferred: real model/transport/prompts, cancellation/timeouts for real inference, per-request user-selected context subsets, richer validation error details, multiple exercise links in the UI, proposal persistence/audit lineage, interactive end-to-end native smoke. Automated UI checks here cover source wiring and command behavior; they are not a claim of live interactive verification. No chat/avatar/reactions/memory, natural-language mutations, task evaluation or autonomous recommendations. Stop for review.

Final verification: root `npm test` and `npm run build` PASS (Core, Analytics, HumanCoach, Companion, Desktop, Mobile compatibility and all workspace typechecks). Companion was rerun after adding hostile-structure/dependency tests: 22/22 PASS. Desktop proposal/storage suite: 15/15 PASS, alongside the existing identity/picker/storage/lifecycle tests. Hardcoding/import/side-effect audits and `git diff --check` PASS. Existing Mobile chunk-size warning and expected corrupt-storage fixture diagnostic are non-failing. Package-lock changes only register the new local workspace and Desktop dependency; no external model packages were installed.
