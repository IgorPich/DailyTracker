# HumanCoach context v1

HumanCoach records accepted or proposed information from an external human trainer or external ChatGPT trainer. It neither recommends nor executes training changes. No Analytics, Companion, AI or shared-kernel dependency.

## Package and public contract

`packages/human-coach/src/domain/context.ts` owns readonly CoachNote, CoachTask, CoachTarget, CoachDecision, Provenance, Acceptance, HumanCoachContext and validation. `application/humanCoach.ts` exports typed creation, acceptance, task-status and target-retirement commands through `createHumanCoach`. `ports/contextRepository.ts` defines the transactional repository and a read-only list of canonical exercise IDs. `tests/` covers the actual domain/application behavior. There are no unused evidence ports or empty layers.

All commands receive IDs and canonical UTC timestamps from their caller; the domain uses no clock, randomness or user-specific defaults. IDs are opaque exact strings. Creation and acceptance reject unknown or duplicated exercise definitions; names and aliases are not exposed to the package. Existing context whose linked exercise was subsequently deleted remains stored, and Desktop displays the unresolved ID without correcting it. No Tracking write port exists.

## Authority and provenance

Every creation command produces DRAFT, even for manually entered items. Only `acceptCoachItem({ id, acceptedAt })` produces AUTHORITATIVE. The domain rejects repeated acceptance and acceptance before creation. Draft tasks cannot change lifecycle status; draft targets cannot be retired. No extraction or automatic promotion exists. `listContext` includes clearly distinguished drafts and accepted items for management; `listAuthoritativeContext` filters drafts out. It retains closed tasks and retired targets as context, not instructions to execute.

Every item has immutable `id`, `createdAt`, provenance and content through the application API. Provenance contains MANUAL or TRAINER_TEXT, `createdAt` matching the item, optional free-text `sourceReference`, and optional `sourceNoteId`. Structured TRAINER_TEXT items require an existing source note created no later than the derived item. A raw pasted CoachNote itself is the source and does not need another note. Referencing a note does not accept that note or its siblings: acceptance is per item. Source links may therefore point to draft source notes; the full management context retains them.

CoachNote preserves text including whitespace. No update/delete/source-replacement command exists. Repository snapshots are detached; the Desktop repository additionally rejects replacing/removing persisted note source content. Corrections/versioned source editing are deferred.

## Structured items

- CoachTask: title, optional description, zero or more exact exercise IDs, OPEN/COMPLETED/CANCELLED. After acceptance all distinct transitions, including reopening, require a command. Append-only status history records the status, timestamp and optional manual evidence note. Equal timestamps are allowed; chronological reversal and no-op transitions are rejected. No due-date model or automatic evidence evaluation.
- CoachTarget: title, acceptance and ACTIVE/RETIRED lifecycle. Constrained specifications: BODYWEIGHT/PERSON/positive kg value; WAIST/PERSON/positive cm value; REP_RANGE/EXERCISE/exact exerciseId/positive integral min–max/reps. These are trainer-defined values, not Analytics or Tracking settings. Targets can be explicitly retired after acceptance. Other targets, deadlines and target revisions are deferred.
- CoachDecision: immutable text and optional exact exercise IDs. Records a trainer decision, but has no execution mechanism. Template/workout mutations remain separate explicit Tracking actions.

## Desktop and persistence

`HumanCoach.tsx` is a lazy Desktop page reached through “Kontekst trenera” in the sidebar. Existing bottom navigation and Android are unchanged. It supports manually saving source notes (typed or pasted), tasks, targets and decisions as drafts, choosing a source note, exact-ID exercise selection, explicit acceptance, task status changes and target retirement. Provenance, timestamps, source links, acceptance, IDs and task history remain inspectable. No automatic parsing, chat input, recommendations or source edits. Existing CoachReport notes remain unchanged; there is no implicit migration between the old report notes and this context.

Authoritative local storage is separate from synchronized AppData and Tracking SQLite:

- Packaged Desktop: `$APPDATA/greekgod-human-coach.v1.json` under Tauri's application-specific AppData directory, Store envelope `{ context: { version: 1, items: [...] } }`.
- Development Desktop: `greekgod-human-coach.dev.v1.json`, additionally under the existing dev application identifier when using tauri:dev.
- Browser preview: the corresponding filename is a dedicated localStorage key; dev/prod keys are separate, and browser data is not migrated to the installed app.

The singleton LocalHumanCoachRepository serializes read-modify-write and acknowledges only completed saves. Browser tabs also use Web Locks. Reads access native disk; corrupt JSON, missing context, invalid records or unsupported versions fail closed without resetting/repairing. Merely opening the page/importing the module does not write a file. The native fixed-path command now saves the same v1 Store envelope using atomic replacement and verified backup, not Store cache. An additive capability permits exists/read only for the two named HumanCoach files; existing Tracking capability/schema/protocol are unchanged. See [hardening checkpoint](4.0-human-coach-hardening.md).

## Limits and deferred decisions

- Windows native writer exclusivity is now enforced by a session-local process guard before Tauri initialization. Browser Web Locks cover tabs on the same origin; unavailable locks fail rather than silently downgrade. Other operating systems have not been certified by this Windows checkpoint.
- Verified rolling backups and atomic replacement are implemented. Recovery is explicitly manual, not automatic; see checkpoint procedure. Existing Tracking backups, reset and phone sync do not include HumanCoach. No production deployment is performed.
- Local files are not encrypted. Provenance references are labels, not verified external sources. Local file tampering is outside the trust boundary; validation is a corruption/invariant guard, not cryptographic authentication.
- No task evaluation, target evaluation, Tracking mutation, AI, trainer extraction, evidence-reader implementation, Companion or strategic recommendations.
- Browser page behavior is typechecked and source-wiring checked; transport tests use injected native/browser I/O doubles. Real isolated Windows Tauri creation/restart, single-writer behavior and backup persistence now pass. This is not a complete interactive UI acceptance test or production installation.

## Verification

HumanCoach tests cover source immutability, source links, authority separation, explicit audited transitions, exact generated IDs, same-name/alias independence, unknown/duplicate/deleted definitions, constrained targets, validation and dependency boundaries. Desktop tests cover native/browser adapter round-trips, no initialization writes, namespace isolation, failed-write recovery, corrupt-data refusal, immutable notes, detached snapshots and read-only Tracking/UI wiring. Normal workspace test/typecheck/build includes the new package and Desktop suite. Runtime contains no user exercise IDs/names, gyms, calorie/weight targets or dates.
