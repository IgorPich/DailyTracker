# Configurable Journal — implementation and review report

Feature branch: `feature/4.0-configurable-journal`. Approved Configurable Journal
runtime HEAD is `56ecc53ceb670ea12df06984269f61e33baedec2`. The persistent foundation and
pre-LLM checkpoint remain at that commit. Feature only: no merge, deployment or
production database inspection/migration.

## Domain and storage

Core owns the system `JournalMetricDefinition` registry: stable ID, label, canonical
unit, integer constraint, optional legacy field, and fresh-install tracking default.
The registry is metadata, not the user's selected fields. Configuration lives in
`settings.journalConfiguration`: version 1 and ordered metric tracking records with
`metricId`, `initiallyTracked`, and chronological `{from, tracked}` transitions.
Configuration order determines field order; IDs never depend on names or position.

`DailyEntry` retains its existing ID/date/optional legacy fields and note. New metrics
use `measurements: Record<metricId, number>`; CHEST and BICEPS use centimetres. The
single `measurementValue` accessor reads existing metrics from their legacy fields
and new metrics from the map. Legacy values are NOT copied/dual-written into the map.
Unknown existing keys and inactive values survive a touched-field save unchanged.
No user-custom metric/unit creation is offered.

Canonical units: kg (weight), cm (circumferences), count (steps), kcal (calories), g
(macros). Decimal comma and dot are parsed through Core, not browser numeric coercion.
Blank touched input means CLEAR; untouched input means UNCHANGED; no missing-to-zero
conversion. Sleep/recovery legacy fields have no established unit contract in this
codebase: retain raw historical numbers and label them as historical values, without
inventing hours, scales, conversions, or a completion interpretation.

No DailyEntry content migration or AppData version bump. Without stored configuration,
the old seven displayed fields remain tracked in their existing form order:
weight, waist, calories, protein, carbs, fat, steps. Chest/Biceps default off. Existing
sleep/recovery observations remain accessible and cause those legacy metrics to be
included in the derived legacy configuration. Derivation never persists anything.
Saving configuration is an explicit settings entity mutation, not an upgrade side effect.
Program templates, definitions, exercise IDs, workouts and seeds are unchanged.

## Tracking history and UI

Settings → Dostosuj dziennik edits a detached local draft. Save uses the native
authority capability; cancel/discard has no persistence side effect. Enable, disable,
re-enable and reorder are supported. Effective dates are inclusive. Same-day changes
have one final state for that calendar date; editing before an already recorded later
transition is rejected rather than silently replacing later tracking history.

An inactive date is NOT_TRACKED, even if a preserved historical measurement exists.
An active date without a finite measurement is MISSING_DATA. No recommendations are
generated from inactive dates. Coverage is measured tracked days / tracked days, with
null coverage and null average for an entirely untracked interval. No average is
invented when there are no measured tracked days. Queries use explicit inclusive dates.

Desktop and Mobile forms enumerate active configured metrics for the selected date.
Desktop history retains columns with historical values even when currently disabled.
Disabling a metric neither clears values nor deletes history. Mobile receives PC
configuration through the existing settings entity; it does not edit the configuration.
The read-only browser Desktop preview does not gain an unsafe fallback save capability.

Desktop persistence is the existing serialized native authority queue plus fresh load,
touched-field/configuration baseline check and revision CAS. Only durable acknowledged
state is published as APPLIED; stale/unknown outcomes require refresh/review. Local
Mobile uses the existing queue, reloads fresh authority, validates touched fields and
preserves all others. A known CAS failure may repeat this validation once; an unknown
acknowledgement never auto-retries. This is local field intent, NOT cross-device merging.

## Analytics, reporting and Companion

`journalMetricSummary` is generic, read-only Analytics over Core metadata/configuration.
It exposes daily statuses, measured/tracked/untracked/missing counts, coverage and
average. Desktop CoachReport shows the generic table and includes metric status/counts
in copied text. Existing specialized cards use a derived availability-filtered view.
Dashboard no longer prompts for a weight/waist measurement when tracking is disabled.

The seven-day weight algorithm itself is unchanged (D-6..D, available finite values).
Only its read input is filtered by tracking periods/current report endpoint. Historical
data remains in the Journal and generic period facts. The chart tooltip's `/7` remains
calendar-window information, distinct from generic tracked-day coverage.

`companionJournalEvidence` exposes calculated status/coverage facts through the existing
read-only evidence shape, tested with the actual read-only Companion runtime and a
synthetic model. No Tracking object or writer is passed to Companion. The existing
reaction diagnostic page deliberately remains synthetic; no live LLM, automatic
dialogue trigger, additional action or production-data feed was added to it.

## Approved schema 7 → 8 safety prerequisite

Migration 8 adds only two STRICT tables in the existing migration transaction:

| Table | Metadata |
| --- | --- |
| `daily_delivery` | service_id + operation_id key/FKs, original_remote_base, status, authority_revision, created_at |
| `daily_conflict_rejections` | operation_id key, device_id, entity_id, original_base, authority_revision, original request_json, created_at |

No previous migration/checksum changes, no payload rewrite, no global/materialized
revision increase for metadata alone. A late migration error rolls back the entire
migration and preserves the schema-7 database and outbox.

New client DailyEntry outbox writes freeze the known remote entity base in the SAME
transaction that creates the operation. Pull cannot replace this base. A conflict
durably marks NEEDS_REVIEW; pending selection excludes it without blocking unrelated
operations. Original payload and operationId remain inspectable and unchanged.

The authority records a conflicting operationId durably, rejecting every later reuse
even with a newer base or altered payload. A manual fresh reviewed edit uses a NEW ID;
it can succeed and its successful retry is idempotent while the old ID remains rejected.

Legacy quarantine applies only to unacknowledged client outgoing DailyEntry rows lacking
original-base provenance. Migration identifies clients by registered outgoing
`sync_remotes`; Desktop authority publication stores have no outgoing sync remotes.
Already acknowledged/applied rows and unrelated entity rows remain unchanged. Preparing
an old unpaired queue after pairing also quarantines missing provenance, never fabricates
a base. The authority's ordinary publication enumeration remains unchanged. This role
assumption is explicit: an authority acting as an outgoing replication client would
require a separate design decision, not inference from names or payloads.

Mobile Settings shows affected dates, preserved payloads and manual refresh/reapply
instructions. The old intent remains an immutable review record (there is no automatic
discard, dismissal, or claim that the conflict was resolved). Multiple queued edits
against the same remote base can conservatively require separate review.

Schema8 ↔ schema8 works; schema7 requests are rejected before mutation by the existing
exact-schema handshake/request gate. Protocol stays 1: conflict responses already exist,
and new delivery state is local metadata. No redundant capability flag. The release
must coordinate Desktop/Sync and Mobile schema8; do not connect schema7 clients expecting
automatic upgrade. Production deployment remains separately authorized work.

## Verification and limits

All tests use fixtures, mocks or isolated temporary databases, never production/phone.
Coverage includes default/cancel/reorder, activation periods, historical preservation,
normalized JSON round-trip, decimal input, unknown/inactive fields, one-per-date,
fresh CAS and stale same-field rejection, lost acknowledgement, and Desktop publication.
SSR/evidence checks verify NOT_TRACKED and unchanged weight arithmetic.

Native regression executes MobileSyncEngine over two real SQLite stores: Mobile weight
edit, PC newer weight + Chest/Biceps, conflict, fresh pull, repeat sync and both stores
reopened. PC values survive; unrelated workout still syncs; zero stale retry. A buggy
client changing X's base/payload stays rejected; reviewed Y succeeds exactly once.
Migration fixtures cover empty client, unrelated pending, unproven legacy pending,
authority publication and previously applied rows; failure injection proves rollback.
Existing tombstones/no-resurrection, cursor atomicity, entity revision, idempotency,
push/pull and two-process contention/restart/WAL regressions were rerun.

Automated native/SSR coverage was not itself an interactive installed-app or
Android-device UX acceptance run. Browser preview remains non-writing for the new
Desktop persistence capability. The later isolated physical acceptance is recorded
below and does not authorize production deployment.

### Physical schema-8 acceptance — PASS

The controlled physical-device smoke completed with synthetic data only. Desktop used
identifier `com.igorpich.formlog.schema8smoke`, AppData
`C:\Users\igorp\AppData\Roaming\com.igorpich.formlog.schema8smoke`, and its isolated
`greekgod-v3.sqlite`. Android used the visibly labelled TEST package
`com.igorpich.greekgod.mobile.schema8test`, separate from the stable Mobile package.
The local handshake and pairing succeeded with protocol 1 and schema 8. No pairing
nonce, device token, certificate fingerprint or other pairing secret is retained in
this report.

Physical results:

1. Configurable Journal enabled Chest and Biceps, disabled an existing metric and
   reordered a metric. Save plus Desktop restart preserved activation and exact order.
2. Chest and Biceps values synchronized phone ↔ PC. A subsequent Weight-only Mobile
   edit preserved both untouched measurements.
3. A recorded value survived disabling its metric, editing another field and restart;
   re-enabling the metric restored the unchanged historical value.
4. On `2026-09-16`, Desktop authority held Weight `82.0`, Chest `101.0` and Biceps
   `41.0` while stale Mobile proposed Weight `81.0`. Sync did not replay the stale whole
   payload: Desktop values survived and the Mobile DailyEntry operation entered the
   review/quarantine state.
5. After app/service restart and another sync, the quarantined operation still did not
   replay automatically.
6. The unresolved DailyEntry conflict did not block unrelated safe sync: Mobile
   `2026-09-17` Weight `77.7` reached Desktop while the earlier operation remained
   quarantined.

Final physical result: **PASS** for isolated schema-8 Desktop/Mobile compatibility,
Configurable Journal durability, inactive-value preservation and conservative
DailyEntry conflict safety. Isolated test data was preserved after stopping only the
smoke Desktop and Sync Service processes. This is not a production-data, installer,
upgrade or deployment acceptance.
