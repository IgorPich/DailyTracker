## 1. Current storage

Core DailyEntry has id/date, optional weight, calories, protein, fat, carbs, steps,
waist, sleep, recovery and note. Authoritative SQLite stores each daily_entry as JSON
in sync_entities.payload_json, identified by date. The app_data JSON is a verified
materialization, not an independent source of truth. Revisions/outbox/tombstones and
order metadata are maintained by the existing repository transaction.

legacy_bootstrap::project_snapshot/project_array clone whole daily_entry payloads;
reconstruct_with_connection reconstructs the arrays without a metric whitelist.
Settings is an existing singleton JSON entity (`settings/global`). Root-level AppData
keys are explicitly reconstructed: an arbitrary new root journalConfiguration property
would not automatically survive projection/reconstruction. Nesting configuration in
settings avoids that specific problem.

Mobile native commands accept serde_json::Value; sync validation checks daily_entry.date
against entity ID, not individual metric fields. Therefore generic JSON transport can
carry additive nested measurements. This is not proof of safe editing by existing clients.
Current repository schema version is 7; sync PROTOCOL_VERSION is 1 and handshake schema
compatibility uses the storage schema version. Shared AppData version is 4.

## 2. Exact compatibility boundary: stale Mobile edits

Mobile journalDraft spreads the loaded entry; applyJournalNumericDraft preserves unknown
keys already loaded. This ordinary case is safe for an additive measurements object.

But JournalPage constructs a complete `entry` OUTSIDE its mutate updater. That updater
calls Core upsertDailyEntry(current.dailyEntries, entry), which replaces the whole same-day
record. MobileDataContext retries the SAME updater against fresh authority after a CAS
conflict. It does not merge touched fields onto the fresh entry.

Reproduction using current functions, synthetic data only:

1. Mobile opens a day without generic measurements.
2. Desktop adds CHEST/BICEPS to that same day.
3. Mobile edits weight using its older draft.
4. A final CAS conflict refreshes authority, then retries the captured replacement.
5. New measurements disappear from the desired payload and may be durably synced away.

A loaded older CHEST value can similarly overwrite a newer value and delete a newly added
BICEPS key. JournalPage's draft effect depends on existing.id/date, not updated contents;
same-ID reload does not by itself guarantee draft refresh. The same captured-entry/updater
pattern was verified in the current main source. This is a pre-existing whole-record
conflict limitation, not a metric serializer whitelist or proof of production data loss.

Tests in apps/mobile/tests/journal-compatibility-preflight.test.ts characterize both the
safe ordinary case and the unsafe retry. Assertions of loss document the current STOP
condition, NOT desired future behavior; replace them with preservation regressions when
the compatibility repair is approved. No production data was read or changed.

## 3. Proposed model (not implemented)

- System JournalMetricDefinition registry: stable IDs; value type, canonical unit,
  validation and display metadata. Include all existing numeric metrics plus CHEST/BICEPS;
  note stays a preserved text field. Existing sleep/recovery units/validation need explicit
  source/fixture characterization before exposing new controls; do not guess their meaning.
- JournalConfiguration under settings.journalConfiguration, versioned nested contract:
  metric display order separate from dated tracking transitions/periods. Validate known
  IDs, unique ordering, valid dates and non-overlapping deterministic lifecycle.
- DailyEntry.measurements keyed by stable metricId for additional metrics, using canonical
  values (circumferences cm). No new fixed chest/biceps fields.
- One normalized Core accessor maps legacy metric IDs to existing fields and additional
  IDs to the generic map. Never store a legacy metric in both locations or dual-write it.
- Legacy fields remain authoritative for existing measurements during compatibility phase.

Tracking semantics: legacy metrics historically tracked before explicit configuration;
new metric activation starts at an explicit effective date, never inferred from missing
values. A disabled period yields NOT_TRACKED, enabled absence MISSING_DATA. Later re-enable
does not reinterpret the intervening period. Existing measurements remain readable even
in disabled periods. Define same-day transition policy explicitly; date-granularity cannot
represent multiple different intra-day tracking states.

## 4. Proposed migration/defaults

Prefer a lazy compatibility view, no rewriting legacy DailyEntries. Absent configuration
derives the current seven-field input order (weight, waist, calories, protein, carbs, fat,
steps). Preserve sleep/recovery values and account for existing usage when introducing
their controls; do not silently disable previously used metrics. Legacy numeric metrics
are historically tracked; no fabricated values. Chest/Biceps are opt-in, not an upgrade
side effect. Persist configuration only after explicit user Save, using fresh-authority
program-scoped-style validation/CAS applied to configuration, not stale whole AppData.

## 5. Sync and Mobile impact / approval needed

Additive JSON representation itself appears not to require new SQL tables, entity types
or a protocol bump. However the existing Mobile writer is NOT proven lossless and the
user's explicit STOP condition is triggered. Desktop-only non-sync storage is not assumed
authorized as an alternative.

Proposed prerequisite: approve a narrow Mobile daily-entry edit compatibility repair:
capture explicit field edits/clears and apply them to the fresh same-day entry inside the
existing retry, preserving untouched/unknown values. Cover same-day creation collisions,
stale drafts, CAS retry, intentional deletion and conflicts on the same edited field.
Desktop Journal's new-entry-on-existing-date replacement path needs equivalent preservation
when configurable inputs are implemented. Do not broadly alter unrelated workout writes.

Updating repository source does not protect already installed old clients. Before enabling
new synced measurements, approve a rollout/compatibility policy: require verified compatible
Mobile installation, or negotiate/reject incompatible writers. Current protocol/schema
versions do not distinguish a safe writer from the existing one. If enforced negotiation
requires a capability/protocol change, that needs separate explicit approval; no numeric
version bump or deployment policy has been silently selected here.

## 6. Rollback/data-loss risks

Old Mobile may remove unknown/newer measurements during whole-entry retry. Rolling back
Desktop/Mobile to an old writer can reintroduce this even when JSON remains parseable.
Legacy-field removal or dual-writing normalized duplicates would add further divergence
risk and is not proposed. Any eventual deployment needs verified backups, compatible
writer policy and reverse-compatibility tests; no backup/repair/deployment was performed.
