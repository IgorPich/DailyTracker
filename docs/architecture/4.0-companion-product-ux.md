# GreekGod 4.0 Companion product UX

Status: feature branch; stop for review. This slice composes the already approved
read-only Companion, explicit-command safety, ReactionCoordinator and managed local
runtime. It does not change model prompts, schemas, decoding, grounding, lifecycle,
storage schemas, sync protocol or executable capabilities.

## Product surfaces and authority

Desktop navigation now exposes `Companion` as the normal conversation surface and
`Polecenie dla aplikacji` as a deliberately separate mutation surface. The ordinary
composer creates only `UserDialogueInput` and calls `createReadOnlyCompanion` with the
managed local model. It has no `ActionDefinitionRegistry`, `TrackingCommandGateway`,
Tracking writer, HumanCoach writer or Companion Memory writer. Mutation-like prose in
chat remains read-only and can only direct the user toward the separate command flow.

The explicit-command page uses the same managed provider to prepare the one existing
`ChangeTemplateRepRange` proposal. Its established proposal, preview, explicit
confirmation, stale validation, typed gateway, durable persistence and receipt chain is
unchanged. Fake remains a deterministic test/development provider. Ollama remains a
development and benchmark transport; neither is a product fallback.

## Request-scoped context and session state

The Desktop context adapter selects a small context for each request:

- deterministic 30-day training-time facts only for a training/analytics question;
- accepted authoritative HumanCoach items only for a trainer-context question;
- accepted, active global structured memory only for a memory question.

The adapter is read-only and exposes the model only bounded `{ id, text }` evidence.
The response must return exact supplied evidence IDs under the existing closed
validator. The UI resolves those IDs to local friendly labels and never displays raw
internal IDs. No evidence badge is shown when the model selected no real evidence.
HumanCoach remains the external-trainer authority; an explanation creates no Trainer
draft or authoritative item.

Conversation turns exist only in React component memory and are discarded when the
surface unmounts. There is no transcript store, restart replay, or transcript-to-memory
conversion. The dialogue contract cannot return a `MemoryCandidate`; the existing
structured-memory review path retains explicit accept/reject and is not invoked by
normal chat.

## Managed-model UX and failures

The Companion page reduces detailed runtime states to four user states: not installed,
loading, ready and temporarily unavailable. Missing or invalid runtime/model assets
provide a calm route to Settings → Companion AI and explicitly preserve full Tracking
availability. Starting and active inference show a lightweight loading state. Cold
requests start the already approved managed runtime; warm requests reuse it. The
approved 300-second idle policy is unchanged.

Timeout, malformed output, sidecar failure and checksum failure are caught without a
Tracking write and without rendering technical errors, stack traces, PID, port, token
or llama-server details. Settings remains the technical readiness surface. There is no
downloader, hosting URL, installer, automatic update, cloud provider or Ollama fallback.

## AvatarPresenter

`AvatarPresenter` is the sole UI mapping from existing `AvatarPresentationState` to a
small local visual. Its closed mapping covers `NEUTRAL`, `ACKNOWLEDGE`, `POSITIVE` and
`CONCERNED` with a symbol and accessible label. The page observes only
ReactionCoordinator snapshots; priority, queue, cooldown and expiry remain coordinator
responsibilities. With `prefers-reduced-motion`, the presenter uses a static/minimal
presentation while preserving semantic meaning.

The model cannot select symbols, assets, animation names, CSS classes, timing or color.
No remote assets, animation dependency, 3D rendering or runtime asset download was
added. Final character artwork remains a later visual-design concern.

## Development tooling

The useful memory-inspection and reaction-diagnostic pages remain in the source tree
but their navigation is gated by `import.meta.env.DEV` and labeled as development
tooling. Fake configuration and raw diagnostic surfaces are therefore not normal
product navigation.

## UI layout

The product page consists of a header; compact avatar/readiness card; optional calm
installation or retry notice; current-session transcript with collapsible friendly
evidence; composer with send/loading/error states; and a separate command-boundary card
linking to `Polecenie dla aplikacji`. The layout collapses to a single column at the
existing mobile-width breakpoint, although Companion remains a Desktop product surface
in this slice.
