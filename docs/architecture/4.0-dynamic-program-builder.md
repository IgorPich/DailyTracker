## User workflow and identity

Settings → **Edytuj program** opens a separate local sandbox. Template cards support
add, rename, reorder (drag/drop or arrows), duplicate and confirmed removal. Exercise
cards support exact-definition picking, replacement, addition, duplication, removal,
prescription/set-count editing and within-template reordering. Technical IDs are not
displayed. Existing Tracking screens are not redesigned.

Drafts are detached copies. Editing, dragging and Cancel do not call persistence or
publish draft templates to Tracking/Analytics. Closing/navigation discards the draft;
there is no autosave or navigation-away warning. Explicit Save applies the full program.
The unchanged-draft Save button is disabled; the persistence API also handles a no-op
without revision/outbox growth. Browser/legacy storage may edit a sandbox but cannot save
through an unsafe fallback.

Existing template and slot identities survive rename/reorder. Duplicate template creates
new template and slot IDs, references the same definitions and copies prescriptions.
Duplicate slot gets a new slot ID, not a new definition. Replacement changes only the
selected slot's definition reference/display snapshot/sensitivity. History and definition
library are never edited by this capability. Removing a template never cascades into
workouts; historical template names/codes remain snapshots.

At least one saved template is required. Generic validation allows 1–100 templates,
at most 200 slots/template and 1–100 sets/slot. Empty templates are allowed. IDs are
nonblank/unpadded, template IDs unique, slot IDs unique within each template, and every
exerciseId must match exactly one current definition. Names/labels/prescriptions must
be nonblank strings (maximum 2,000 characters). Prescriptions retain the existing free-text
contract, including complex notation; no new rep-range grammar or training strategy is
imposed. Array positions represent order; no name/letter/ID sorting.

## Durability/concurrency

Desktop-only `ProgramPersistence.saveProgram(ProgramPlan)` is not a Companion capability.
Core owns detached draft, canonical program baseline, validation, patch and duplication.
Reordering delegates to existing Core moveItem; no second storage queue is introduced.

1. Clone request; join NativeAuthorityAppDataStore's existing serialized queue.
2. Read latest authoritative AppData and revision inside the queue.
3. Compare only the program baseline (sorted object keys, ordered arrays). Unrelated
   revisions, daily entries, workouts or settings do not invalidate this baseline.
4. Changed program → STALE_PROGRAM, no write. Invalid draft/reference → VALIDATION_FAILED.
5. Replace only templates on the fresh aggregate, preserving all other fresh fields.
6. Existing native CAS and multi-entity SQLite transaction handle delta, outbox, tombstones,
   materialization and commit together. One user save is one change-set; its revision delta
   is the actual entity mutation count, not necessarily one revision.
7. Await confirmed durable result before React publication. Reconciliation does not call save.

Final CAS conflict returns STALE_PROGRAM even if the intervening change was unrelated: it protects
the read-to-write race, not the sandbox opening revision. Disk failure with unchanged
revision is PERSISTENCE_FAILED. Uncertain acknowledgement is INDETERMINATE, never retried
automatically; fresh read indicates whether the desired program is present, not attribution
of the write. Failed reconciliation holds ordinary edits and both safe capabilities until
authority returns. UI requires refresh/review after stale/failed/uncertain results.
HumanCoach/Companion files are outside this aggregate and are not touched.

## Next Configurable Journal slice — audit only

Current DailyEntry has id/date and optional weight, calories, protein, fat, carbs, steps,
waist, sleep, recovery, note. There is no metric registry or persisted tracking-enable
state. Desktop Journal fields/priorities/table, Mobile JournalPage/mobileModel input
metadata, weight/waist calculations, Dashboard/Progress/CoachReport and CSV columns are
field-specific. CSV currently omits model fields sleep/recovery.

Sync represents a daily_entry keyed by date with a JSON payload and revision/order
metadata, not a SQL column per measurement. A new metric payload may not need a physical
SQL migration, but requires a reviewed shared data contract, validation, export and old-client
round-trip compatibility. A new entity kind would change the closed sync discriminator.
Do not equate flexible JSON storage with guaranteed protocol compatibility.

Safest next direction: preserve current fields/history/configuration as defaults, add an
explicit versioned metric/configuration contract and effective tracking periods. Disabling
must not delete history; MISSING_DATA vs NOT_TRACKED must be explicit, not inferred from
absence. No journal implementation or migration is included here.
