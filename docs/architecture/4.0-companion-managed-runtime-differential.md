# Managed Companion runtime differential investigation

Status: prompt/schema quality gate passed on the feature branch; **experimental, stop for review, do not merge into foundation**. The product model remains `Phi-3.5-mini-instruct-Q4_0.gguf` with SHA-256 `b5374915da534cb93df39f03bd4f2cd5a0c533df0d5e21957dc9556c260be9eb`. All inputs below are synthetic.

## Quality-hardening result

The unchanged original nine cases and nine added generalization cases pass on both Ollama and managed llama.cpp b10760. All 18 final structured outputs are byte-identical across providers. The reproducible raw record is `evidence/managed-runtime-quality-v2.json`.

Four bounded request contracts replace the earlier generic contract: `greekgod-trainer-v2`, `greekgod-dialogue-v2`, `greekgod-memory-v2`, and `greekgod-command-v2`. The transport wrapper remains `greekgod-companion-v1`. TrainerText uses discriminated TASK/TARGET/DECISION schemas and an empty list for no safe proposal. Explicit command parsing has a closed `NO_PROPOSAL` alternative. Read-only dialogue separates exact evidence `{id,fact}` use from the answer and only adds the no-mutation boundary for mutation-like dialogue.

Entity grounding is request-local and ephemeral. Exact, unique supplied names may deterministically narrow a request. Otherwise the model must return an allowlisted ID plus a verbatim source span selected from bounded spans derived from that request. The app checks the allowlist and exact occurrence before the existing domain validator. These spans are neither stored nor accumulated; there is no global or persistent name-to-ID map, fuzzy merge, or model authority over identity. Generic range/measurement parsing only constrains values actually present in the source and cannot create a proposal kind or entity. Focused tests prove numeric-only, unrelated and ambiguous inputs remain empty.

The managed implementation now pins b10760 commit `0f3a71be15af836d277c9f918adfafb45732677e`, uses raw `/completion`, the exact Phi wrapper, raw `json_schema`, and the fixed decoding values below. Its minimal runtime contains 24 manifest-pinned files: the server executable/implementation, llama/common/mtmd, ggml/base/Vulkan, every selectable CPU backend, libomp and its license. Runtime verification rejects missing, modified, or extra files before launch. Model acquisition remains separate and manual.

Lifecycle policy for a later slice: startup performs no model load; first AI use starts and loads it; a configurable internal five-minute idle timeout should stop the sidecar and release VRAM; application exit always stops it. The current slice preserves on-demand startup and exit shutdown and deliberately does not add idle optimization.

Final quality matrix (schema ON, fixed parameters, 16 September 2026):

| Corpus | Ollama | Managed b10760 | Exact output parity |
|---|---:|---:|---:|
| Original, unchanged | 9 / 9 | 9 / 9 | 9 / 9 |
| Added synthetic generalization | 9 / 9 | 9 / 9 | 9 / 9 |

The added cases cover another TASK/TARGET/DECISION, ambiguity, no exercise, an unrelated allowlisted entity, exactly one supported entity among multiple candidates, a numeric evidence answer and mutation-like read-only dialogue. No original expectation, model, quantization, identity boundary or ambiguity rule was weakened.

A live synthetic inference from the minimal staged runtime sampled four socket states and observed `NON_LOOPBACK_COUNT=0`. The ten runtime-directory modules loaded by that process were `llama-server.exe`, `llama-server-impl.dll`, `llama-common.dll`, `llama.dll`, `mtmd.dll`, `ggml.dll`, `ggml-base.dll`, `ggml-cpu-haswell.dll`, `ggml-vulkan.dll`, and `libomp.dll`; every one is in the checked manifest. b10760 did not exit through its best-effort `/shutdown` request within the bounded wait, so the existing owned-child kill-and-wait fallback ran; a post-audit process check found no managed-runtime process or listener. An unrelated Ollama-owned runner remained until benchmark shutdown. This is process/socket sampling, not packet capture.

## Exact prompt and decoding comparison

The GGUF has no embedded `tokenizer.chat_template`. Its metadata says `add_bos_token=false`, `add_eos_token=false`, BOS ID 1, EOS ID 32000, Phi context capacity 131072 and original RoPE context 4096. Ollama injects a separate 149-byte template layer:

```text
{{ if .System }}<|system|>
{{ .System }}<|end|>
{{ end }}{{ if .Prompt }}<|user|>
{{ .Prompt }}<|end|>
{{ end }}<|assistant|>
{{ .Response }}<|end|>
```

The rendered inference prefix used for parity is therefore exactly:

```text
<|system|>
[greekgod-companion-v1] [{request-specific contract version}] {system instruction}<|end|>
<|user|>
{JSON input}<|end|>
<|assistant|>
```

Ollama's model layer defines four stops: `<|system|>`, `<|user|>`, `<|end|>`, `<|assistant|>`. The harness supplies the same stops to llama.cpp raw completion. Both sides receive context 4096, maximum 512 generated tokens, temperature 0, seed 42, top-k 40, top-p 0.9, min-p 0.1, repeat-last-n 64, repeat penalty 1, presence penalty 0 and frequency penalty 0. The request-specific system text, JSON input, ID/evidence allowlists and JSON schema are produced by the application's `buildLocalInferenceRequest`; the harness does not maintain a divergent prompt copy.

Ollama renders its model-layer template before its native llama backend. The prototype instead used llama.cpp's OpenAI-compatible chat endpoint and `response_format`. That is not equivalent. Raw `/completion` with the exact rendered prefix and `json_schema` is equivalent for b10760.

## Historical fixture differential before quality hardening

At b10760 + exact raw template + schema ON, the Ollama and managed output strings are identical in all rows:

| Fixture | Both providers | Gate |
|---|---|---|
| Trainer TASK with Polish diacritics | TASK with exact `exercise-zuraw` | PASS |
| Trainer TARGET 6..8 | TASK describing the target, not a TARGET specification | FAIL |
| Trainer DECISION | TASK, not DECISION | FAIL |
| Ambiguous TrainerText | TASK linked to both `press-a` and `press-b` | FAIL — guessed association |
| Mutation-like read-only dialogue | cites `count-1`, but does not answer “4” or clearly state no deletion | FAIL |
| MemoryCandidate | GLOBAL SUMMARY_STYLE SHORT, `expiresAt=null` | PASS |
| Hostile data | schema-valid empty-ID TASK; no secret or mutation capability | PASS bounded/safety gate |
| Invalid-reference text | attaches the only allowed but semantically unrelated ID | FAIL — should reject association |
| CHANGE_TEMPLATE_REP_RANGE | exact `candidate-1`, min 6, max 8 | PASS |

Schema OFF demonstrates why grammar cannot be removed: both providers produce prose, multiple JSON values, markdown or wrong fields, and application validation rejects all nine. Schema ON remains mandatory and is still followed by the existing strict application validator.

## Root cause and recommendation

The strongest evidence is the b10760 raw/schema-ON run: nine out of nine output strings are byte-for-byte equal to Ollama. The model asset, prompt, template, stops and decoding can therefore reach exact parity outside Ollama. The original regression came from two integration deltas:

1. b7081 is far behind the installed Ollama's pinned b10760 lineage and emits different/whitespace-suffixed constrained output in several cases.
2. llama.cpp's OpenAI chat `response_format` path is not equivalent to Ollama's separately rendered raw Phi prompt; on b10760 it fails grammar initialization for every evaluated schema.

Recommendation: **Case B**. Retain the feature as experimental and do not merge. A reviewed implementation may switch the managed transport to checksum-pinned b10760 plus exact raw Phi rendering and raw-completion JSON schema, while preserving the existing authenticated loopback lifecycle and strict validator. Before promotion, a separate prompt/schema quality change must make both providers pass the unchanged full gate. This investigation does not authorize weakening fixtures, changing the model/quantization, accepting guessed IDs, or treating transport parity as product quality.

For clarity: Case A would promote because parity and the complete quality gate pass; Case B proves a bounded integration correction but quality work remains; Case C would abandon this model/runtime path because parity cannot be obtained. Evidence supports B.

## Reproduction and evidence

Run the harness with Node's type stripping and explicit local paths; it refuses non-loopback Ollama endpoints and reads only the synthetic fixture:

```powershell
node --no-warnings --experimental-strip-types scripts/managed-runtime/differential-harness.mjs `
  --llama-server <isolated-runtime>\llama-server.exe `
  --model <isolated-model>\Phi-3.5-mini-instruct-Q4_0.gguf `
  --revision b10760-0f3a71be15af836d277c9f918adfafb45732677e `
  --schema on --transport raw --ollama http://127.0.0.1:11434 `
  --out <result.json>
```

The eight raw result files in `docs/architecture/evidence/` preserve every rendered prompt, schema, endpoint request body, raw synthetic output, latency, token counts and gate result for b7081/b10760 × raw/chat × schema on/off. They contain no token, runtime/model path or production datum.

The earlier process audit remains valid for the unchanged lifecycle: dynamic authenticated loopback, different port/token after forced restart, zero observed non-loopback sockets during inference, and all ten loaded modules inside the 37-file verified inventory. This differential changed neither lifecycle nor network code.
