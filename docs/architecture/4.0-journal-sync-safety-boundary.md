## Current and approved local flow

Current JournalPage captures a full entry before calling mutate. MobileDataContext retries
that updater after a local CAS conflict, replacing fresh same-day fields. Existing Mobile
characterization tests demonstrate deletion of unknown fields and stale value resurrection.

Approved replacement: immutable baseline for the selected date plus explicit touched
fields with SET(value) / CLEAR actions; omitted fields mean untouched. In the existing
serialized queue, load current local authority, compare only touched-field presence/value
against baseline, and overlay valid changes on the fresh same-day entry. Preserve unknown
fields, existing entry identity and one-entry-per-date. Deletion/recreation and ambiguous
same-day matches require conflict review. Same-field change returns STALE without write;
unrelated fields merge. On final CAS retry re-read and revalidate the SAME field baseline.
Only acknowledged durable persistence publishes success; uncertain acknowledgement must
not trigger replay. UI refresh/review follows conflicts; no redesign required.

This can fix LOCAL Mobile persistence, but does not fix the second replay below.

## Proven second replay: Mobile SQLite → PC authority

crates/greekgod-sync-client/src/lib.rs performs push_pending → pull_all → push_pending
again after a remote conflict. remote_sync_repository::prepare_operation substitutes the
latest remote revision from sync_remote_entities but retains the original outbox payload.
The outbox persists full entity payloads, not touched fields with baseline values.

New test `journal_preflight_rebased_outbox_can_overwrite_newer_remote_fields` uses two
temporary NativeAppDataStores and the actual repository methods:

1. PC day weight=80 is pulled to Mobile.
2. Mobile saves weight=79 into its native outbox.
3. PC changes weight=81 and adds CHEST=100/BICEPS=35.
4. Original Mobile push correctly conflicts.
5. Mobile pulls PC changes, prepares the SAME outbox payload with the NEW remote revision.
6. PC accepts the retry: weight becomes 79 and measurements disappear.

The test reproduces repository behavior driven by the current client sequence; it is not
a live network/phone test or evidence that production has experienced this scenario.
It intentionally asserts current loss as a STOP characterization, not desired behavior.

Even an upgraded field-aware UI would still generate full native outbox snapshots and
could take this path. Pending entries created by a pre-fix binary also survive upgrade;
advertising a safe capability for the new executable alone would falsely bless those edits.

## Handshake, authentication and authority defence

CompatibilityRequest currently contains app_version, protocol/schema ranges, device_id
and last_server_revision. There is no capability field. HandshakeResponse has versions
and revision, no negotiated capability. Every push includes CompatibilityRequest; HTTP
authorization binds its device_id to paired credentials and engine checks operation IDs
against that device. Protocol=1, schema=7.

An OPTIONAL serde-defaulted capability set is a plausible additive extension; missing
means unsupported. Absence of a current capability field does NOT prove a version bump
is mandatory. Enforce any future requirement on every push, not only initial handshake,
and only after the writer and its queued operations genuinely satisfy it.

PC currently validates identity and entity CAS, but receives no field intent/baseline.
After the rebase above the revision is valid, so CAS cannot detect stale field values.
Rejecting all missing keys cannot distinguish intentional CLEAR from accidental omission;
it also misses same-key stale overwrites. Broad server merge would conceal real conflicts.
No such heuristic has been added.

## Decision required before implementing the mechanism

The boundary is established native sync conflict semantics, not merely missing JSON fields.
Do not label the prerequisite solved with a local form fix plus a capability string.

Two possible designs need review:

1. Conservative DailyEntry conflict policy: never automatically rebase/replay a conflicting
   full DailyEntry outbox payload. Preserve pending intent for explicit review; quarantine
   unverifiable pre-upgrade pending entries rather than delete or re-label them. A designed
   conflict-review path is needed because a pull currently changes local materialized state.
   This can potentially avoid protocol/schema bumps, but unrelated REMOTE conflicts also
   stop instead of being field-merged. It changes the current sync conflict model.
2. End-to-end field intent: durably retain touched fields, explicit clears and original
   baselines across offline/restart and sync. Validate those against PC authority before
   constructing the full replacement. This requires a reviewed outbox/operation contract
   extension (potential schema/protocol migration), not an ephemeral React-only patch.
   Existing pending operations cannot have their missing intent safely fabricated.

No numeric version bump is claimed inevitable for option 1. For option 2 the exact wire/
storage design and versioning must be approved before migration; none is silently chosen.
The user explicitly forbids casually changing sync conflicts/substantial sync redesign,
so this additional boundary is returned for review before implementing either mechanism.

Proposed capability policy after that decision: old clients remain usable with matching
3.x authority; a 4.0 authority with configurable measurements rejects DailyEntry writes
without SAFE_DAILY_ENTRY_FIELD_MERGE (or the final semantically accurate capability).
Enforcement must also prevent an old Settings writer removing the authority requirement,
and must be checked atomically with mutation/activation to avoid races. Do not enable
generic measurements or advertise this capability before the chosen end-to-end guarantee
and pre-upgrade queue policy are tested. Product version is not a safety capability.
