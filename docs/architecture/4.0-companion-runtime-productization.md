# GreekGod 4.0 Companion runtime productization

Status: feature branch; stop for review. This slice does not change the approved Phi model, prompts, schemas, decoding parameters, authoritative grounding, or Companion capabilities.

## Lifecycle

The managed model is not started with GreekGod. The first managed inference verifies all assets, starts one authenticated loopback b10760 process, and loads Phi. Requests are serialized; queued and active requests both prevent idle shutdown. Each completed success or failure advances a generation and schedules a new idle deadline. A stale timer cannot stop a newer generation. After five minutes with no active or queued inference the owned process receives a bounded graceful shutdown, followed by a forced stop if necessary. A request racing `STOPPING` waits and then creates at most one new instance. Application exit invalidates timers and immediately stops the owned process.

The product default is 300 seconds. The timeout is injected internally in Rust tests so concurrency and timer behavior can be verified quickly without changing the shipped value. Status distinguishes `RUNTIME_MISSING`, `RUNTIME_INVALID`, `MODEL_MISSING`, `MODEL_INVALID`, `READY_UNLOADED`, `STARTING`, `READY_WARM`, `INFERENCE_ACTIVE`, `IDLE_UNLOADED`, `STOPPING`, and `FAILED`.

### Physical resource measurement

On 2026-09-16 an isolated test-root run exercised the production 300-second timeout with the checksum-verified Phi asset. Values are Windows process working set, `Win32_OperatingSystem.FreePhysicalMemory`, and the process-scoped `GPU Process Memory` dedicated-usage counter:

| State | Managed PID | Working set | Free physical RAM | Dedicated VRAM |
|---|---:|---:|---:|---:|
| A: application/native harness open, AI unused | none | 0 | 41,160,110,080 bytes (38.333 GiB) | 0 |
| B: model warm after inference | 14208 | 2,282,119,168 bytes (2.125 GiB) | 38,798,254,080 bytes (36.134 GiB) | 3,814,973,440 bytes (3.553 GiB) |
| C: after the default idle stop | none | 0 | 41,173,938,176 bytes (38.346 GiB) | 0 |
| D: harness closed | none | 0 | 41,168,465,920 bytes (38.341 GiB) | 0 |

The test completed in 339.97 seconds. The warm PID disappeared, its measured working set and dedicated VRAM returned to zero, and C had 13,828,096 more free physical bytes than A. These are host-specific point measurements, not general hardware requirements; shared GPU memory, driver allocations, and sampling variance are not attributed by the selected counters.

## Assets and explicit installation boundary

The authoritative current-user root is the application local-data directory plus `companion-managed-runtime`. Its layout is:

- `runtime/llama.cpp-b10760/`: exactly the 24 files in the pinned runtime manifest;
- `models/Phi-3.5-mini-instruct-Q4_0.gguf`: SHA-256 `b5374915da534cb93df39f03bd4f2cd5a0c533df0d5e21957dc9556c260be9eb`;
- `manifests/`: pinned runtime and future model distribution manifests;
- `licenses/`: redistributable license and notice files.

For non-production test identifiers only, `GREEKGOD_MANAGED_RUNTIME_ROOT` may redirect this root to isolated synthetic/test assets. Production ignores that override. Runtime readiness requires the exact file count and every compiled-in hash; missing, extra, or modified runtime files and a changed model are rejected before process start. GreekGod never repairs, replaces, downloads, or updates these assets silently.

The final isolated fixture audit found exactly 24 runtime files, 24/24 matching manifest hashes, zero extra files, and the expected model SHA-256. That manually staged development fixture predates the acquisition script's new `manifests/` and `licenses/` copies and is test evidence only, not a redistributable package. A future explicit runtime acquisition stages the checked-in manifest and llama.cpp license; the model and its authoritative license/provenance remain a separate manual distribution requirement.

Settings exposes a deliberate “Install local AI” information action. It explains approximate 2.3 GB disk use, on-device inference, transient multi-GB RAM/VRAM use, and that Tracking remains complete without AI. It currently provides manual layout guidance only. No production download URL, provider SDK, updater, or Ollama fallback is wired because a trusted GreekGod distribution channel has not been approved.

## Authentication and network boundary

b10760 documents the API-key environment variable as `LLAMA_API_KEY`. Earlier prototype code used the ignored name `LLAMA_ARG_API_KEY`; a productization verification demonstrated that an invalid token was then accepted. This branch corrects the managed runtime and synthetic harness to `LLAMA_API_KEY`, verifies both acceptance of the generated instance token and rejection of a deliberately invalid token, binds only dynamic `127.0.0.1`, disables the web UI, selects offline mode, and restricts CORS to localhost. In the product runtime, tokens and prompts never appear in command arguments, logs, or temporary files. The opt-in development quality harness records only synthetic rendered prompts in its explicit result file and never records its token.

During the synthetic 27-case dual-provider run on 2026-09-16, process-attributed TCP sockets were sampled ten times from 19:44:27 through 19:44:46 Europe/Warsaw. The sampled processes were managed `llama-server.exe` PID 1820, Ollama PID 1668, and Ollama's worker PID 4044. Every connected remote address observed for those PIDs was `127.0.0.1`; listeners had the Windows unspecified remote address `0.0.0.0` and were locally bound to `127.0.0.1`. No non-loopback connected remote was observed. The managed process exited with the harness. `pktmon status` was unavailable on this host, so this is repeated process/socket observation rather than packet-level proof or a claim about driver internals.

The same run passed all unchanged acceptance gates with semantic parity: original 9/9 on Ollama and managed, generalization 9/9 on both, and grounding-adversarial 9/9 on both. All 54 provider/fixture results were accepted by the application validator. Inputs were synthetic only.

## Non-goals preserved

There is no cloud fallback, automatic alias generation, additional Companion action, quality prompt change, model substitution, automatic update, or production Fake/Ollama fallback. Tracking persistence and production data are outside this runtime boundary.
