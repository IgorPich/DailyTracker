# Conservative DailyEntry conflicts — schema STOP

The conservative policy is approved. This supersedes the policy-choice question in
4.0-journal-sync-safety-boundary.md, but implementation has encountered the explicit
section-6 migration STOP. No migration or runtime change has been made.

## Why current schema cannot represent the required state cleanly

Schema 7 sync_outbox has immutable operation identity/payload, local base/result revisions,
attempt_count, last_attempt_at and acknowledged_at. pending_outbox selects every row with
acknowledged_at IS NULL. There is no conflict/quarantine state or immutable first-sent
remote base revision. sync_remote_entities contains only the latest remote revision and
prepare_operation substitutes it into pending requests.

An in-memory blocked set does not survive restart. acknowledged_at means accepted, so
using it to hide a conflict would falsely record success. attempt_count cannot safely
encode conflict: transient errors also increment it. Putting control metadata into a
DailyEntry payload would contaminate synchronized user data/request hashes. A sidecar
file would introduce a second, non-transactional store and crash-consistency problem.
These are not safe substitutes for dedicated metadata.

The authority has a second persistence gap. applied_operations records only successful
SyncMutationResult values, requires positive result_revision, and deserializes replay as
success. CAS conflicts return before insertion; apply_mutation rolls back on that error.
Thus the same conflicted operationId can later be accepted with a different baseRevision.
Reusing this success ledger for rejected operations needs a schema/contract change, not
a fabricated successful result/revision.

## Proposed small additive migration: 7 → 8 (NOT implemented)

Keep existing migrations/checksums, payloads, entity revisions, materialization and
successful-operation idempotency unchanged. Add two dedicated metadata tables:

1. Mobile remote-operation delivery state, keyed by serviceId + operationId, linked to
   the existing outbox. Store frozen first-sent remote base revision, explicit status
   (pending/needs_review), observed conflicting remote revision, and timestamp. Original
   payload, date/entity ID, local base revision and operationId remain in the outbox.
   Freeze remote baseline transactionally BEFORE first send, not only after receiving
   conflict, so a crash cannot silently generate a newly rebased retry.
2. Authority conflict ledger, keyed consistently with the current operationId idempotency
   namespace, recording device/entity identity, original request/hash and base revision,
   observed authority revision and conflict timestamp. A conflict commits metadata but
   NO entity mutation/outbox/global revision. Subsequent submissions of that operationId
   remain rejected even if baseRevision changes. Successful idempotent replays continue
   using the existing applied_operations ledger.

Persist NEEDS_REVIEW before pulling fresh PC state; normal send queries exclude it across
restarts, while a separate review query exposes the preserved pending payload and current
authority. Do not auto-delete/acknowledge conflicted entries or create replacement operation
IDs. Explicit conflict resolution is a separate, user-reviewed action. Apply the approved
policy only to DailyEntry; preserve unrelated entity/tombstone conflict semantics.

Old pending payloads remain intact. Their stored base_revision is LOCAL, not necessarily
the remote revision used in a prior push. Historical first-sent remote revisions may be
unrecoverable; mark unavailable provenance explicitly, never invent it. Previously attempted
legacy entries without trustworthy wire-baseline metadata need conservative review/hold
rather than treating today's remote revision as their original baseline. Never infer SET/
CLEAR field intent from those payloads. Migration policy for these rows must be approved.

The first-send/failure/acknowledgement/review transitions require crash and restart tests,
including a lost conflict response. This is durable conflict bookkeeping, not a merge engine.

## Handshake/version consequence

Current SyncEngine::handshake advertises store.probe().schema_version. Mobile currently
pins schema_min=schema_max=7 and separately requires handshake.schema_version==7. Therefore
schema 8 cannot be introduced transparently: existing clients will reject the new authority.
The advertised sync schema compatibility must change along with SQLite schema 8. This is
the exact version boundary triggering STOP, even though DailyEntry JSON need not change.

Protocol v1 JSON could still accept an optional serde-defaulted capability set: old messages
omit it, old serde implementations ignore it. No protocol-number bump is shown necessary
for that additive field alone. Proposed semantic capability:
SAFE_DAILY_ENTRY_CONFLICT_HANDLING. Do not advertise it until local field-aware writes,
durable conflict quarantine, legacy pending policy and native no-replay behavior all work.

On activated 4.0 configurable authority, reject DailyEntry mutations lacking capability,
on EVERY push with authenticated device binding. Protect requirement activation/removal
atomically, including older settings writers. Old clients may continue with their unchanged
matching 3.x service; they cannot be silently granted write access to the migrated authority.
No hardcoded app-version identity rule, broad server merge or last-write-wins is proposed.

## Remaining approved implementation after migration approval

Mobile local path: baseline + explicit touched SET/CLEAR fields; serialized fresh local
authority read; same-field conflict rejects, unrelated/unknown fields survive; existing
CAS revalidates field baseline on retry; durable-first success. Native path: conflict
persists NEEDS_REVIEW, retains original intent, refreshes authority, never rebases/replays.
Only after both paths and the capability gate are verified may Configurable Journal proceed.
