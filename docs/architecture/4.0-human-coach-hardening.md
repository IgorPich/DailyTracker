# HumanCoach deterministic-foundation hardening checkpoint

No changes to HumanCoach domain, provenance, acceptance semantics, UI, v1 file envelope, Tracking schema or sync protocol.

## Windows single writer

`desktop_instance.rs` creates a session-local named Windows kernel mutex handle, keyed by the Tauri application identifier, before Builder/plugins/windows initialize. A second handle sees ERROR_ALREADY_EXISTS, closes its own handle and returns normally (exit 0), before any writer can initialize. Failure to acquire also fails closed. The guard handle lives through the application event loop; normal close or process termination releases it. Dev and smoke identifiers are separate from production. No file locking or domain locking is added. Second-launch focus is deliberately not implemented; the existing window stays usable and the second process safely exits without a scary dialog.

The official Tauri single-instance plugin was inspected but is not a dependency: downloaded Windows implementation v2.4.4 exits a duplicate only when its first-instance messaging window is found. The interval between mutex creation and messaging-window creation therefore leaves a startup race. The minimal native handle guard does not depend on a window existing. Scope of verification: current Windows Desktop; older unguarded binaries or externally edited files cannot be made safe by this new binary.

Writer audit: only Desktop HumanCoach persistence writes its file. Sync Service, Mobile and background helpers have no HumanCoach writer/import. Browser uses localStorage, not native AppData; development uses `.dev.v1.json`. The one process plus the existing repository queue serializes native writes. No redundant inter-process file lock.

## Atomic native save and backup

`human_coach_save` accepts a context and dev/prod selector, not an arbitrary path. It resolves the current application's AppData directory and the existing fixed HumanCoach filename. The application validates full domain data; native code additionally validates JSON and v1 envelope before any write.

Before each replacement:

1. Read the complete previous file, refusing corrupt JSON/invalid envelope. For first creation, use the initial complete snapshot as backup contents.
2. Write those exact bytes to a unique temporary file in the same directory; flush and sync the file; reread and compare; atomically replace `<filename>.backup.json`; reread and verify the backup.
3. Write the new v1 envelope to another same-directory temporary file; flush and sync; reread and compare; atomically replace the authoritative filename.

Uses `tempfile::NamedTempFile::persist`, implemented on Windows with MoveFileExW(REPLACE_EXISTING). The destination is never opened with truncation. A backup failure prevents replacing authority. A failure before replacement preserves old authoritative bytes. A crash before replacement may leave an orphan temporary file but cannot turn it into authority. After replacement the file is a complete new snapshot. This is interruption safety, not a guarantee against arbitrary hardware/filesystem failure or power-loss metadata durability.

Backup is one rolling previous snapshot beside the standalone file, not Tracking's database-specific pre-import backup mechanism. It preserves the entire JSON file including its envelope and previous formatting. It is not an independent-device disaster-recovery copy. Older backups are replaced atomically; no retention framework is introduced.

## Explicit recovery decision

No automatic restore exists. Invalid main data produces an error without overwriting either main or backup. There is no timestamp-based attempt to decide that backup is newer.

Manual recovery is a separately authorized operation: close Desktop, preserve both current and backup files, validate the proposed backup with `validateHumanCoachContext` after extracting its context, inspect its source/provenance/acceptance, compare against any newer valid main file, and obtain explicit approval for the exact replacement. A newer valid main file must never be silently replaced. Then use a same-directory atomic replacement, reopen and verify the exact chosen snapshot. This checkpoint does not execute recovery on production. A dedicated recovery/export UI and additional retention remain deferred.

- Build from Desktop: `npm run tauri:human-coach-smoke:build`.
- Run `apps/desktop/scripts/run-human-coach-smoke.ps1 -Fresh` from PowerShell.
- The smoke mode uses `com.igorpich.formlog.humancoachsmoke`; it does not mount AppProvider or execute Tracking/bootstrap/sync.
- Fresh mode preserves previous isolated smoke data in a timestamped sibling, with exact-path validation; it never archives production.
- Real WebView calls the actual application service/repository/native save. It creates a source note and task, explicitly accepts the task, saves exact expected context in its test result, and stays running.
- The script launches a second process, verifies exit 0, exactly one remaining writer PID and a responsive first window, unchanged HumanCoach bytes, normal close, later launch, exact full-context equality and unchanged backup bytes after restart.
- Production JSON/SQLite/WAL/SHM top-level file hashes are read before and after and must match. No production HumanCoach file is created.
